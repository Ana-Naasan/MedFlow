    2b. Gemini API call (core.py)
    ────────────────────────────────────────────────────────────────────────

    - response_mime_type="application/json" enforces structured output.
    - temperature=0.0 for deterministic results.
    - API key read from GOOGLE_GENAI_API_KEY env var at call time.
    ✅ Good.

    ⚠️  No error handling for Gemini API failures:
       If the API is unreachable, the key is invalid, or rate limits are hit,
       the exception propagates uncaught.  The PRD (REASON-08) expects
       abstention ("no well-supported explanation found") when nothing can
       be produced — not a crash.
       RECOMMENDATION: Wrap the API call in try/except and return [] on
       transient failures.

    2c. Response parser (core.py)
    ────────────────────────────────────────────────────────────────────────
    - Handles empty/whitespace responses → ValueError.
    - Handles malformed JSON → ValueError.
    - Handles non-dict top-level → ValueError.
    - Handles non-list hypotheses → ValueError.
    - Non-dict entries in the hypotheses list are silently skipped.
    - Non-dict citations in a citation list are silently skipped.
    - Missing fields get sensible defaults (severity="moderate",
      confidence="low", citations=[]).
    - Hypothesis IDs are generated as hyp-1, hyp-2, etc.
    ✅ Thorough input validation.

    2d. Citation verifier (core.py — REASON-02)
    ────────────────────────────────────────────────────────────────────────
    - Patient-fact citations checked against tags in the flattened text.
    - Evidence-card citations checked against known snippet IDs.
    - If ANY citation in a hypothesis fails, the entire hypothesis is dropped.
    - Unknown citation kinds are left as-is (not verified, not dropped).
    ✅ Structural anti-hallucination is implemented.

    ⚠️  The verifier checks against the *flattened text* rather than the
       *cache* directly.  The PRD §13 says "every patient_evidence id must
       exist in cache."  Checking the text is a reasonable approximation
       (the text is built from the cache), but it means a tag that appears
       in the text due to a rendering bug would pass verification.
       For Phase 2 this is acceptable, but note for future tightening.

3.  ARCHITECTURE ALIGNMENT
================================================================================

    3a. Citation kind naming
    ────────────────────────────────────────────────────────────────────────
    The existing codebase uses citation kinds:
      - cache/store.py: kind="resource", kind="evidence"
      - PRD §14:       kind="patient"|"openFDA"|"DDInter"|"Beers"|"ACB"

    The new reasoning code uses:
      - kind="patient_fact"   (instead of "resource" or "patient")
      - kind="evidence_card"  (instead of "evidence" or "openFDA"/etc.)

    ❌ MISALIGNMENT: When the reasoning output flows into the existing
       DecisionPacket DTO and is consumed by the frontend, the kind field
       will not match what the frontend expects.  The frontend citation
       rendering (FE-01/02) may check for specific kind strings.

       RECOMMENDATION: Either:
       (a) Align the reasoning output to use the existing conventions
           ("resource" for patient facts, keeping evidence source-specific
           kinds like "openfda_adverse_event"), OR
       (b) Update the Citation DTO documentation and the frontend to accept
           the new kind vocabulary — but this is a wider change.

    3b. Citation ref format (brackets)
    ────────────────────────────────────────────────────────────────────────
    The new code stores patient-fact refs WITH brackets:
      ref="[MedicationStatement/ms-001]"

    The existing store.py uses refs WITHOUT brackets:
      ref="Patient/pat-001"

    The verifier tags are extracted WITH brackets from the flattened text,
    so the internal consistency is fine.  But when these refs are served to
    the API consumer (e.g. the citation-resolution endpoint), the consumer
    receives "[MedicationStatement/ms-001]" — with brackets — while the
    existing convention sends "Patient/pat-001" — without brackets.

    ⚠️  MISALIGNMENT: Consumers calling /patients/{id}/resource/{rtype}/{fhir_id}
       receive the resource type and fhir_id from URL params, not the ref string,
       so the functional impact is low.  But mixed conventions will confuse
       frontend developers and break any consumer that parses the ref field.

       RECOMMENDATION: Strip the square brackets from patient-fact refs, or
       explicitly document the ref format in the Citation DTO.

    3c. Integration with /packet endpoint
    ────────────────────────────────────────────────────────────────────────
    The reasoning core is NOT wired into the api/packet.py endpoint or the
    cache.  This is expected for a Phase-2 unit-level task — the end-to-end
    wiring will happen when the reasoning core, cache, and API are connected.
    Not flagged as a deviation.

    3d. Dependencies / requirements.txt
    ────────────────────────────────────────────────────────────────────────
    google-genai==2.7.0 added.  ✅ Clean.

4.  POTENTIAL ISSUES
================================================================================

    4a. Error resilience
    ────────────────────────────────────────────────────────────────────────
    See 2b above — no try/except around the Gemini API call.  If the
    API call fails, the entire /packet endpoint would return 500 instead
    of gracefully degrading.  REASON-08 requires abstention.

    4b. Kind-specific verifier gap
    ────────────────────────────────────────────────────────────────────────
    The verifier only checks citations with kind="patient_fact" or
    kind="evidence_card".  Any citation with an unrecognised kind (e.g.
    a hallucinated kind the model invents) passes verification silently.
    Since the prompt controls what kinds the model uses, this is low-risk,
    but a strict verifier should drop any citation whose kind is not
    in a known set.

    4c. EvidenceSnippet coupling
    ────────────────────────────────────────────────────────────────────────
    The run_reasoning() signature takes Sequence[EvidenceSnippet] from
    backend.app.knowledge.openfda.  The PRD envisions multiple knowledge
    sources (DDInter, Beers, ACB) each producing their own evidence format.
    A more flexible type (e.g. a Protocol or dataclass union) would allow
    other knowledge sources to feed the reasoning core without modifying it.
    Acceptable for Phase 2 scope (openFDA only).
